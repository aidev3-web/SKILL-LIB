# TechNext HTML editor (edit-in-place, bilingual-safe)

## What this is for

Trung already has a finished HTML file — a daily report, a morning plan, or a slide deck — made by one of the three `technext-*` authoring skills, and now wants a targeted change: fix a typo, update a number, add a missed task, remove a slide, correct a date. Rebuilding the whole file from scratch risks losing edits he made by hand afterward and wastes time re-deriving content that was already right. This skill instead edits the existing file directly, in place, while keeping every structural rule the original authoring skill already validated: the bilingual span pairing, the placeholder/auto-count logic, the inline-SVG icons, and the untouched CSS/script shell.

This skill only **edits content**. It does not regenerate a file from raw notes (that's `technext-daily-report` / `technext-morning-plan`), does not create a new deck (`technext-slide-deck`), and does not send email or publish anything — those stay separate, deliberate steps the user asks for explicitly.

## Step 1 — read the whole file and identify its type

Read the target file completely before touching anything — a partial read risks missing a section whose structure you then get wrong. Identify which of the three templates it is from concrete markers, not the filename alone (a renamed or copied file won't tell you):

| Signal in the HTML | Type | Matching source skill |
|---|---|---|
| `class="t-vi"` / `class="t-en"` spans, a `.stat-tile` row, section cards titled Đã hoàn thành/Đang thực hiện/Vướng mắc/Kế hoạch ngày mai | **Daily report** | `technext-daily-report` |
| `class="t-vi"` / `class="t-en"` spans, `.task-card` with checkboxes, a source-check strip (`.src-item`), `.sess-note` sessions | **Morning plan** | `technext-morning-plan` |
| `class="vi"` / `class="en"` spans (no `t-` prefix), `<section class="slide" id="...">`, `<nav class="dots">` | **Slide deck** | `technext-slide-deck` |

The two span-class conventions are easy to confuse — daily report and morning plan use `t-vi`/`t-en`, the slide deck uses plain `vi`/`en`. Match the file's actual convention; do not introduce the wrong one when adding new content, or the language toggle silently stops working for that piece of text.

If the file matches none of these signals, say so — it may be a hand-edited or unrelated HTML file, and this skill's assumptions (placeholder classes, auto-count scripts, the toggle pattern) may not hold. Ask how the user wants to proceed rather than guessing a structure onto it.

## Step 2 — never touch the shell

Regardless of type, these are already tested and working — do not modify them as part of a content edit:

- The `<style>` block (all CSS: colors, layout, responsive breakpoints, print styles).
- The `<script>` block(s) (language toggle, stat-tile/progress auto-counting, dot-nav sync, checkbox state).
- The inline-SVG logo and icons — never replace one with an `<img>`, emoji, or base64 raster image.
- The overall page shell / section order, unless the user explicitly asks to reorder or restructure.

If a requested change genuinely requires touching the shell (e.g. a real bug in the toggle script, not just content), say so explicitly and confirm before doing it — that's a bigger change than "editing content" and affects more than this one file if the user later copies the same shell elsewhere.

## Step 3 — make the edit, respecting each type's own rules

Apply the change using the same rules the authoring skill already follows for that type — re-read that skill's `SKILL.md` if unsure of a detail rather than guessing:

- **Bilingual pairs**: whenever you add or change user-visible text, update **both** the VI and EN span in the pair, translating faithfully and keeping both equally concise. Never edit just one side.
- **Placeholder class**: on daily report and morning plan, a span/item with `class="placeholder"` means "not filled in" and is excluded from auto-counts. Filling in real content means removing `placeholder` from **both** the `t-vi` and `t-en` spans; leaving a section intentionally empty means keeping the placeholder class in place so the built-in empty state still triggers correctly. Don't hand-edit the stat-tile numbers or progress-bar percentages yourself — they're computed by the page's own script from what you write.
- **Slide deck**: keep one slide = one `<section class="slide" id="...">`; if adding or removing a slide, update `<nav class="dots">` in lockstep so every `data-target` still matches a real section `id` 1:1. Reuse the existing component classes (`.card`+accent, `.grid`, `table`, `.callout`, `.flow`/`.step`) rather than inventing new ones, matching whatever the rest of that specific deck already uses.
- **Morning plan checklist**: keep checklist steps concrete enough to tick; if adding a step, keep the existing 3–5-steps-per-task granularity rather than either a single vague step or an overly granular list.

Make only the change asked for. Don't use an edit request as an excuse to rewrite unrelated sections, re-translate text that wasn't touched, or "improve" content the user didn't flag.

## Step 4 — save and confirm

Save back to the same file path by default (overwrite in place) — that's what "sửa file này" means. Only save to a new file/path if the user asks for a copy instead. After saving, tell the user plainly what changed (one or two lines is enough) — don't re-summarize the whole file.

If the file lives in multiple synced locations (the daily-report and morning-plan skills save to a local folder, Google Drive, and the conversation), ask whether the same edit should be applied everywhere, or only to the copy in front of you — silently editing just one copy leaves the others stale in a way the user won't notice until they open the wrong one later.

## Judgment calls

If the requested change is ambiguous (e.g. "sửa lại phần kế hoạch" without saying what's wrong), ask what specifically should change rather than guessing and rewriting the whole section. If the edit would break the bilingual pairing, the placeholder/auto-count logic, or the dots-nav/section-id sync, say so and propose the smallest change that keeps them intact instead of silently leaving the file in a broken state.
